## What landed

`agent/internal/apply` is a resumable transaction around the existing renderer. `agent/internal/firstboot`
provisions a fresh install and `bittern first-boot` is the operator entry point. The original branch
made no status package, UI handler, schema change, template change or renderer change. The integration
onto main wires the status package and the UI applier without changing the schema, templates or
renderer.

### Transaction steps

| Step | Effect | Power-loss behaviour |
| --- | --- | --- |
| `generation` | Write rendered files and a manifest under `<state-root>/generations/<n>/` | Journal has no completed step; a rerun starts cleanly |
| `check:<file>` | Run the native checker through `System.RunCheck` | Rerun repeats the check from the journal |
| `write:<path>` | Atomically replace a changed live file through `System.WriteFile` | Rerun writes the remaining files, then health-checks and commits |
| `remove:<path>` | Remove a live file absent from the new generation | Rerun continues the removal set |
| `udev:reload` | Run `udevadm control --reload` when the generation contains `.link` files | The reload is idempotent and is repeated if unrecorded |
| `udev:trigger` | Run `udevadm trigger --action=add --subsystem-match=net` | The add event is repeated; renames are idempotent |
| `udev:wait` | Wait up to 10 seconds for every `Name=` parsed from the rendered `.link` files | A timeout fails the step with the missing names, then rollback runs |
| `stop:<unit>` / `restart:<unit>` | Stop a unit whose files disappear; for every changed unit, restart it when active and start it when inactive, in nftables, dnsmasq, chrony, networkd, Frigate order | The unit action is idempotent and is repeated if unrecorded |
| `health:<name>` | Probe links, addresses, the `cam0` DHCP listener, chrony with the rendered config, the firewall table, Frigate, or caller-supplied service endpoints | A failure starts rollback; a cut before the step is retried |
| `commit` | Mark the manifest applied and atomically move `<state-root>/current` | Rerun repeats the commit, then removes the journal |

Every changed unit uses the `restart:` step, even on generation 1. Apply asks systemd whether the
unit is active, then restarts an active unit and starts an inactive one. A plain `start:` is a no-op
on an already-active unit, so it would leave the old configuration loaded. This covers
`systemd-networkd.service` on a normal boot and the package-started `dnsmasq.service` and
`chrony.service` on the GK41. The carrierless `cam0` QEMU run found the networkd case when first
boot tried to health-check an address that networkd had never configured. The renderer template sets
`ConfigureWithoutCarrier=yes`; apply restarts networkd, and the address appears without a camera
link. See [the QEMU first-boot note](2026-11-14-qemu-firstboot.md) and
[the apply unit lifecycle note](2026-11-15-apply-unit-restart.md).

The journal is `<state-root>/journal.json`. On a live failure it changes phase to `rollback`, writes the
previous generation back, re-triggers udev when either generation has `.link` files, restarts its
units, runs health probes, and marks the failed generation `rolled-back`. A cut during rollback resumes
the rollback rather than starting a new apply.

The udev steps run after the live writes and before `systemd-networkd.service` restarts, so networkd
sees the renamed links and the health probes see `lan0` and `cam0` on stock Debian names. The wait
parses `Name=` from each rendered `.link` file rather than assuming the role names. A rename is not
fully reversible in the running kernel without another add event, so rollback reloads udev, restores
the previous `.link` files, and triggers another add event before waiting for the previous names. If
the previous generation had no `.link` files, rollback still triggers udev after removing them but
cannot name the stock interfaces to wait for; a reboot may be needed to complete that reversal.

Validation order is generation, native checks, live writes, udev activation, units, health, commit. A
validation failure writes no live file. `nft -c` returning only the container netlink permission
error is recorded as a skip with that reason; a ruleset syntax error is a failure.

### First-boot tree

The golden tree is `tests/firstboot/minimal/expected`. A successful first boot with a confident
hardware proposal produces this shape, with the secrets redacted:

```text
etc/bittern/appliance.yaml
etc/bittern/secrets.yaml                  # mode 0600, values redacted
etc/bittern/tls/server.crt                # public certificate
live/etc/nftables.conf
live/etc/dnsmasq.d/bittern.conf
live/etc/chrony/chrony.conf
live/etc/systemd/network/10-lan0.link
live/etc/systemd/network/10-cam0.link
live/etc/systemd/network/10-lan0.network
live/etc/systemd/network/10-cam0.network
state/current
state/first-boot.json
state/identity.json
state/setup-token                          # mode 0600, operator read only
state/generations/1/files/...
state/generations/1/manifest.json
```

The marker contains the marker schema version, the appliance schema version, the applied generation,
the completion time, `nic_roles_confirmed`, `recording_configured`, and owner notes. A NIC proposal
that names both roles writes `network.*.match` into `appliance.yaml`; the renderer then emits the two
`.link` files. Two wired NICs always get both matches, including an ambiguous carrier state, which
leaves the roles unconfirmed and records an owner note to confirm or swap them in the wizard.
Wireless and virtual NICs are excluded from the two-role proposal. An inventory with no usable wired
NIC writes no match and no `.link` file. A confident recording candidate sets
`/var/lib/bittern/media` and names the detected drive by `by_id`; otherwise the config has `drives:
[]` and the marker says recording is unconfigured. No disk is formatted.

Identity is `<state-root>/identity.json`. `secrets.yaml` contains the generated admin password, the
TLS private key and the one-time UI setup token; the token also has an operator copy at
`<state-root>/setup-token` with mode 0600. The certificate SANs contain the hostname and the current
`lan0` address when one is available. The fingerprint is stable across a rerun; deleting the identity
file is the signal to regenerate identity, secrets and certificate.

## Verification

`make test` and `make check` pass. The apply tests cover success, validation failure, health failure,
rollback, skipped `nft -c`, only-changed-unit restarts, no-op reruns, secret rejection in rendered
files, and a simulated power cut before every step boundary. A separate test cuts a rollback and
resumes it. The udev tests cover a generation with `.link` files, a missing rename timeout, rollback
re-triggering the restored link files, and a generation without `.link` files where the udev steps do
not run. First-boot tests cover success, idempotent rerun, unconfident hardware, resume after a cut,
rollback then rerun, rename timeout then rerun, certificate SANs and rotation, the golden config/tree,
and secret-free logs. The CLI was run against a temporary root with `--offline`; the resulting tree
matches the golden shape.

## Integration onto main

BIT-011 was rebased onto main after BIT-006 and BIT-007. The branch now uses main's
`agent/internal/redact` implementation; the duplicate `Set` type was removed, and its writer,
YAML-value, concurrency and test coverage were ported into the shared `Redactor`. Apply and first
boot use the shared structured logger and redactor instead of raw `slog`.

The status builder calls `apply.Inspect` and reports `render.generation` and `render.apply_state`
under schema 1. `Inspect` now returns the latest generation manifest even when the current pointer
stayed on the previous generation, so a failed or rolled-back attempt remains visible. The docs and
status goldens are updated.

`agent/packaging/bittern-first-boot.service` runs `bittern first-boot` after local filesystems and
before `bitternd`, skips when the completion marker exists, and keeps a minimal hardening baseline
with only the writable paths and `CAP_NET_ADMIN` it needs. The daemon's non-mock UI applier
persists `appliance.yaml` and calls the apply transaction; `--ui-mock` and the tests keep the stub.
The non-mock setup checks use `ui.AgentChecks`, which reads the status builder shared with the status
page; `--ui-mock` keeps the sample `ui.MockChecks` data.

## Schema v2 NIC matching

First boot no longer writes `10-lan0.link` and `10-cam0.link` through the apply transaction's
extra-file path. It writes `network.lan0.match.mac` and `network.cam0.match.mac` into the generated
version 2 `appliance.yaml` whenever it names a role from a wired NIC, with `pci` as the fallback when
a NIC has no usable MAC. Two wired NICs always get both matches, even when carrier is ambiguous. An
ambiguous carrier state chooses the roles deterministically by PCI address and MAC but leaves them
unconfirmed and records an owner note. Wireless and virtual NICs do not affect the two-role proposal.
The renderer emits the `.link` files with the do-not-edit header, and apply installs them through the
normal generation, validation, and rollback path. An inventory with no usable wired NIC emits no
match and no `.link` file, keeping the logical name as the kernel interface name. The POC runbook now
treats the `.link` files as renderer output and verifies them instead of authoring them by hand.

First boot also writes `hardware.detector` from the detected accelerator and
`hardware.video_decode.acceleration` from the render-node evidence. A render node is recorded as
`vaapi`; without one the value is `none`. Detection does not claim QSV.

## Deferred recording pool mount units

The schema accepts the version 2 `storage.recording.drives` list, including `by_id`, `serial`, and
`device_role` selectors and the empty unconfigured list. The renderer still does not emit systemd
mount units for pool members, does not assemble mergerfs, and does not enforce the free-space reserve
across members. Those are follow-ups for the recording pool from
[ADR 0018](../adr/0018-recording-capacity-pool.md). The `drives` list is already valid and can be
consumed by that work without another schema change.
