# GK41 POC runbook

- Date: 2026-11-14
- Status: hardware-in-the-loop POC checklist, not a reference build
- Hardware: Minisforum GK41, Celeron J4125, 8 GB, dual Realtek Gigabit Ethernet, UHD 600,
  USB Coral, 1 TB USB SATA drive
- Config: [poc-gk41.yaml](../../schema/examples/poc-gk41.yaml)
- Related: [ADR 0005](../adr/0005-dual-nic-isolated-camera-network.md),
  [ADR 0014](../adr/0014-dedicated-recording-drive.md),
  [ADR 0018](../adr/0018-recording-capacity-pool.md),
  [extension points](2026-11-14-extension-points.md)
- Current payload-based checklist: [GK41 POC runbook](../runbooks/gk41-poc.md). This note records
  the earlier manual render and apply path.

This checklist proves two cameras, the dual-NIC split, Coral detection, VAAPI decode, and a
dedicated recording mount on one non-reference machine. It does not change the reference BOM or any
ADR. Record results against OQ-09 and leave the decision there.

The GK41 has an internal 2.5-inch SATA slot. If the 1 TB drive is a 2.5-inch drive, use that slot
instead of the USB adapter. The USB path is a POC path only, not the reference path. Use the USB
adapter only when the drive is 3.5-inch or the internal slot is unavailable.

## Before starting

- [ ] Keep the serial or HDMI console connected for every network and firewall step.
- [ ] Confirm the machine is a GK41 with two Realtek wired NICs and a UHD 600 GPU.
- [ ] Confirm the 1 TB drive is separate from the OS drive. Do not use the OS drive for recordings.
- [ ] Record the current BIOS version, NIC MAC addresses, drive serial, and Coral USB ID.
- [ ] Back up the files listed in [Rollback](#rollback) before changing anything under `/etc`.

## Debian install assumptions

- [ ] Debian 13 (trixie) amd64, minimal install, no desktop.
- [ ] Root filesystem on the internal SATA or NVMe drive, not on the 1 TB recording drive.
- [ ] SSH server enabled, and a local console account that can use `sudo`.
- [ ] `nftables`, `dnsmasq`, `chrony`, and `systemd-networkd` installed.
- [ ] Docker Engine and Compose v2 installed. The POC may use Debian `docker.io` and
  `docker-compose` or the upstream packages; keep the Frigate image digest pinned.
- [ ] Disable NetworkManager or any other service that manages `lan0` and `cam0`. Do not run two
  network managers on the same links.
- [ ] Time zone set to UTC, matching the example configuration.
- [ ] `curl`, `jq`, `lsblk`, and `findmnt` available for the checks below.

## Detect the hardware

- [ ] From the repository, run `make detect`, or build the CLI and run `bittern detect`.
- [ ] Keep the JSON output with the POC notes. Detection is read-only and writes nothing.
- [ ] Check the proposed roles. `lan0` is the NIC with carrier and `cam0` is the other one.
- [ ] If both NICs have carrier, or neither does, the proposal is deliberately unconfirmed. Unplug
  the camera network, bring up one link at a time, and choose by PCI address and MAC.
- [ ] Check the proposed recording disk. If the proposal says USB, treat it as the POC path.
- [ ] Check the proposed detector. The GK41 should propose `coral_usb` when the Coral is attached,
  `openvino` when only the UHD 600 render node is present, and `cpu` otherwise.
- [ ] Read the below-reference note. The GK41 is below the 32 GiB and 14-core reference class, so
  keep the POC at two cameras.

## Match the NICs in appliance.yaml

Use the MAC addresses from `bittern detect`. Do not copy MAC addresses from another machine. The
renderer owns the `.link` files; edit only the configuration.

- [ ] Set `network.lan0.match.mac` and `network.cam0.match.mac` in
  [poc-gk41.yaml](../../schema/examples/poc-gk41.yaml) to the two detected MAC addresses. The
  placeholders in the example are `aa:bb:cc:dd:ee:01` and `aa:bb:cc:dd:ee:02`.
- [ ] Record the MAC that belongs to `lan0` and the MAC that belongs to `cam0` in the POC notes.
- [ ] Do not create `/etc/systemd/network/10-lan0.link` or `10-cam0.link` by hand. They are renderer
  output and are installed in the systemd-networkd step below.
- [ ] An absent `match` means the logical name is the kernel interface name. That is the development
  and QEMU fallback, not the GK41 path.

## Mount the recording drive by ID

The by-id path is in the `bittern detect` JSON and summary. Use the path, not `/dev/sda`, because
device letters can change after a reboot or a USB re-enumeration.

- [ ] Identify the drive and confirm its serial and transport:

```sh
lsblk -o NAME,SIZE,MODEL,SERIAL,TRAN,MOUNTPOINTS
ls -l /dev/disk/by-id
```

- [ ] Confirm the chosen by-id path points at the 1 TB drive and not the OS drive.
- [ ] If the drive is new or can be erased, create one ext4 filesystem on the whole drive. This is
  destructive; verify the serial first:

```sh
sudo mkfs.ext4 -L bittern-media /dev/disk/by-id/usb-USB_SATA_Recording_Disk_USB-GK41-0:0
```

- [ ] Create the mount point and mount it once:

```sh
sudo mkdir -p /var/lib/bittern/media
sudo mount /dev/disk/by-id/usb-USB_SATA_Recording_Disk_USB-GK41-0:0 /var/lib/bittern/media
findmnt /var/lib/bittern/media
df -h /var/lib/bittern/media
```

- [ ] Add one `/etc/fstab` line with the detected by-id path. Do not use `nofail`: a missing
  recording drive is a hard failure, not a silent fallback to the OS drive.

```fstab
/dev/disk/by-id/usb-USB_SATA_Recording_Disk_USB-GK41-0:0 /var/lib/bittern/media ext4 defaults,noatime 0 2
```

- [ ] Run `sudo mount -a` and confirm `findmnt /var/lib/bittern/media` still shows the drive.
- [ ] Confirm `/var/lib/bittern/media` is not on the root filesystem with `findmnt -T`.
- [ ] If using the internal 2.5-inch slot, use the SATA by-id path instead of the USB by-id path.
- [ ] The 100 GiB free-space reserve in the example is a configuration value for later daemon work.
  The renderer does not enforce it in this POC.

## Render the configuration

- [ ] Run the render-only path. It validates the document with the existing config package and
  writes only under the output directory:

```sh
make render-poc CONFIG=schema/examples/poc-gk41.yaml OUT=build/poc-gk41
```

- [ ] Or run the CLI directly:

```sh
bittern render --config schema/examples/poc-gk41.yaml --out build/poc-gk41
```

- [ ] Confirm the tree contains `networkd/`, `nftables/`, `dnsmasq/`, and `chrony/`.
- [ ] Confirm `networkd/10-lan0.link` and `networkd/10-cam0.link` exist and start with the
  do-not-edit header. Each `[Match]` must name the recorded MAC address, and each `[Link]` must name
  the correct role.
- [ ] If a `.link` file is wrong, fix `network.lan0.match` or `network.cam0.match` in the
  configuration and re-render. Do not hand-edit the rendered file.
- [ ] Confirm no secrets or credentials appear in the rendered files.
- [ ] Validate the rendered files on the GK41 before installing them:

```sh
sudo nft -c -f build/poc-gk41/nftables/bittern.nft
sudo dnsmasq --test --conf-file=build/poc-gk41/dnsmasq/dnsmasq.conf
sudo chronyd -p -f build/poc-gk41/chrony/chrony.conf
```

## Apply in order

Keep the console open. The order is deliberate: firewall first, then the camera services, then the
network addresses, so a network mistake is recoverable from the console.

### 1. nftables

- [ ] Copy the current `/etc/nftables.conf` to the backup directory.
- [ ] Load the rendered table once:

```sh
sudo nft -f build/poc-gk41/nftables/bittern.nft
sudo nft list table inet bittern
```

- [ ] The rendered table has no SSH accept rule. For SSH access during the POC, insert a temporary
  live rule after loading, or use the console. Do not edit the generated file:

```sh
sudo nft insert rule inet bittern input iifname "lan0" tcp dport 22 accept
```

- [ ] For persistence, install the rendered file as `/etc/nftables.conf` only if the machine has no
  other nftables policy, then `sudo systemctl enable nftables`. If other rules exist, keep this POC
  table separate and record the extra boot step. The supported management path is not part of this
  POC.

### 2. dnsmasq

- [ ] Back up `/etc/dnsmasq.conf` and `/etc/dnsmasq.d/`.
- [ ] Install the rendered file as `/etc/dnsmasq.d/bittern.conf`.
- [ ] Make sure no other DHCP server is active on `cam0`.
- [ ] Enable dnsmasq but expect it to bind only after `cam0` has its address. The final reboot is the
  activation point.

```sh
sudo systemctl enable dnsmasq
```

### 3. chrony

- [ ] Back up `/etc/chrony/chrony.conf`.
- [ ] Install the rendered file as `/etc/chrony/chrony.conf`.
- [ ] Enable chrony. Like dnsmasq, it may wait for `10.77.0.1` to exist on `cam0`.

```sh
sudo systemctl enable chrony
```

### 4. systemd-networkd last

- [ ] Back up `/etc/systemd/network/`.
- [ ] Install the rendered `.link` files first, then the `.network` files:

```sh
sudo install -m 0644 build/poc-gk41/networkd/10-lan0.link /etc/systemd/network/10-lan0.link
sudo install -m 0644 build/poc-gk41/networkd/10-cam0.link /etc/systemd/network/10-cam0.link
sudo install -m 0644 build/poc-gk41/networkd/10-lan0.network /etc/systemd/network/10-lan0.network
sudo install -m 0644 build/poc-gk41/networkd/10-cam0.network /etc/systemd/network/10-cam0.network
```

- [ ] Enable and start `systemd-networkd` last, then reboot with the console attached. The `.link`
  files are applied by udev during boot, before the `.network` addresses:

```sh
sudo systemctl enable systemd-networkd
sudo reboot
```

- [ ] After reboot, verify the link names and addresses. `ip -br link` shows `lan0` and `cam0` with
  the recorded MAC addresses:

```sh
networkctl status lan0 cam0
ip -br address show lan0 cam0
```

- [ ] `lan0` has a DHCP lease with the default route. `cam0` has `10.77.0.1/24`, no default route,
  and no IPv6 address.
- [ ] If dnsmasq or chrony started before `cam0` had its address, restart them now:

```sh
sudo systemctl restart dnsmasq chrony
```

- [ ] Check that dnsmasq, chrony, and nftables are running after the reboot:

```sh
systemctl status dnsmasq chrony nftables
journalctl -u dnsmasq -u chrony --no-pager -n 50
```

- [ ] The persistent nftables ruleset still has no SSH accept. Use the console, then insert the
  temporary live SSH rule again if SSH is needed.

- [ ] Confirm a camera can get a lease on `10.77.0.50` to `10.77.0.199` and receive NTP from
  `10.77.0.1`. Cameras cannot reach `lan0`, the internet, or the appliance UI.
- [ ] Confirm SSH still works, or use the console. The temporary accept rule disappears on reload.

## First-run UI and setup token

The first-boot unit runs before `bitternd` and leaves the one-time setup token in two places: the
authoritative `setup_token` in `/etc/bittern/secrets.yaml` and a mode 0600 operator copy at
`/var/lib/bittern/setup-token`. First boot prints instructions only, never the token.

- [ ] Read the token on the appliance terminal, or over SSH with the temporary rules in place. Do
  not redirect this command into a file, a log, or a support bundle:

```sh
sudo bittern setup-token
```

- [ ] Confirm the operator copy exists and is root-owned mode 0600:

```sh
sudo stat -c '%a %U:%G %n' /var/lib/bittern/setup-token
```

- [ ] Open `https://<lan0-address>/ui/` from the house LAN and compare the certificate SHA-256
  fingerprint shown by the browser with the setup page and the console output.
- [ ] Enter the setup token once and set the administrator password. The token is single use.
- [ ] Confirm setup removed both copies:

```sh
sudo test ! -e /var/lib/bittern/setup-token && echo setup-token-file-removed
sudo grep -q '^setup_token:' /etc/bittern/secrets.yaml && echo setup-token-still-present || echo setup-token-secret-removed
```

- [ ] If `sudo bittern setup-token` says no token is available, first boot may not have run or setup
  is already complete. Do not fabricate or copy a token from another appliance.

## Frigate fixture with Coral and VAAPI

The Frigate config and compose files are still hand-written fixtures, not renderer output. Start
from [tests/fixtures/frigate](../../tests/fixtures/frigate/README.md) and keep the image digest
pinned.

- [ ] Use `tests/fixtures/frigate/compose.yaml`, not the QEMU variant.
- [ ] Confirm the compose file passes `/dev/dri` and `/dev/bus/usb` into the container and adds the
  numeric `video` (44) and `render` (992) GIDs.
- [ ] Change the media volume from `./state/media:/media/frigate` to
  `/var/lib/bittern/media:/media/frigate` so recordings and the Frigate database live on the
  recording drive.
- [ ] Confirm the host sees the Coral: `lsusb` shows `18d1:9302` or `18d1:9303`.
- [ ] Confirm the host sees the render node: `ls -l /dev/dri/renderD128`.
- [ ] Set the detector in `config/config.yml`:

```yaml
detectors:
  coral:
    type: edgetpu
    device: usb
```

- [ ] Set VAAPI hardware decode in the Frigate config:

```yaml
ffmpeg:
  hwaccel_args: preset-vaapi
```

- [ ] Add the two POC cameras with their `10.77.0.20` and `10.77.0.21` RTSP paths. Use a detect
  substream and keep detection at 5 fps. Use stream copy for recording.
- [ ] Keep the media database under `/media/frigate`, as the fixture already does.
- [ ] Start the fixture and check the detector, camera states, and a recorded clip:

```sh
docker compose -f tests/fixtures/frigate/compose.yaml up -d
docker compose -f tests/fixtures/frigate/compose.yaml logs --tail 100 frigate
docker compose -f tests/fixtures/frigate/compose.yaml ps
```

- [ ] Confirm the Coral detector is active in the Frigate logs. A CPU fallback is a failed Coral
  check, not a pass.
- [ ] Confirm VAAPI is in use for decode. If VAAPI fails, record the error and do not claim hardware
  decode.
- [ ] Confirm recordings and `frigate.db` appear under `/var/lib/bittern/media`.
- [ ] Check for USB resets or drive dropouts in `dmesg` during a 24-hour run.

## Rollback

Do these in reverse order. Keep the console attached until the network is back.

- [ ] Stop the Frigate fixture with `docker compose down`. Recordings and the database stay on the
  recording drive.
- [ ] Remove the temporary SSH accept rule only after another management path is available, or just
  reboot to the saved ruleset.
- [ ] Restore the saved `/etc/nftables.conf` and restart nftables, or delete only this POC table:

```sh
sudo nft delete table inet bittern
sudo systemctl restart nftables
```

- [ ] Stop and disable dnsmasq and chrony. Restore their backed-up configuration files and restart
  them only if they were in use before the POC.
- [ ] Remove the rendered `10-lan0.network` and `10-cam0.network` files. Restore the previous
  network manager or network files.
- [ ] Remove `10-lan0.link` and `10-cam0.link`, then reload udev and reboot so the original
  interface names return.
- [ ] Stop Frigate before unmounting the recording drive. Remove the POC `/etc/fstab` line, then
  `sudo umount /var/lib/bittern/media`.
- [ ] Do not reformat or wipe the recording drive during a rollback. Its ext4 filesystem and
  recordings are independent of the OS configuration.
- [ ] If the network is unreachable after rollback, use the console to restore the backup directory
  and reboot. Do not run a broad `git reset` or `git clean` on the repository.

## What this POC does not cover

- [ ] A/B OS slots and slot switching.
- [ ] OS or application updates, update rollback, and power loss during an update.
- [ ] Reset levels, decommissioning, and media wipe.
- [ ] `bitternd` as a daemon, its API, health model, and apply pipeline.
- [ ] The mergerfs recording pool and multi-drive growth from ADR 0018.
- [ ] The rest of the `bittern-ui` first-run wizard, status page, logs, and support bundle. This
  runbook covers only the setup-token read path.
- [ ] 16 cameras, 8 MP cameras, and the reference 14-day or 30-day retention targets.
- [ ] Camera discovery, ONVIF probing, reservations, and the secrets workflow.
- [ ] Hardware-in-the-loop soak, thermal, power-loss, and SMART validation.

## Record after the run

- [ ] Detected NIC MACs, PCI addresses, and driver versions.
- [ ] Proposed NIC roles and whether the proposal was confirmed.
- [ ] Recording drive by-id path, serial, transport, and measured throughput.
- [ ] Detector actually used, Coral USB ID, and VAAPI decode result.
- [ ] Idle and load power, CPU load at two cameras, and memory use.
- [ ] USB resets, drive dropouts, and any kernel messages during the run.
- [ ] The exact `bittern detect` output, with no secrets, attached to the POC note.
